# Дорожная карта разработки (docs/ROADMAP.md)

В данном документе приведён поэтапный план реализации системы **Telegram Remote Control**. Каждый этап содержит перечень целей, ожидаемых результатов, зависимостей и критериев приёмки.

---

## Принцип последовательности и зависимости этапов

Порядок этапов сформирован по принципу минимизации рисков: наиболее неопределённые и критичные интеграции (особенности Antigravity CLI на Windows и сетевые нюансы WoL) проверяются до построения сложной бизнес-логики.

> [!NOTE]
> **Обоснование изменения последовательности:**
> Допускается параллельное или опережающее выполнение **Этапа 6 (Wake-on-LAN)** до **Этапа 4/5 (Telegram-бот и очередь)**, поскольку модуль отправки сетевых пакетов полностью изолирован и не зависит от логики Antigravity.
> При этом **Этап 3 (Прототип интеграции с CLI)** строго обязателен **до** построения очереди задач (**Этап 5**), так как параметры работы процесса (кодировки, флаги неинтерактивности, обработка сигналов прерывания) определяют контракт взаимодействия исполнителя.

### Этап 4. Реализация Telegram-бота, авторизации и интеграции с AgyClient [Завершён]
* **Цель**: Создание интерфейса Telegram-бота с обработкой базовых команд, строгой аутентификацией пользователей и интеграцией с AgyClient через интерактивное подтверждение.
* **Результат**:
  * Асинхронный Telegram-бот на базе `aiogram` 3.x в режиме Long Polling (без входящих портов и вебхуков).
  * Middleware [`AuthorizationMiddleware`](../src/remote_control/controller/middlewares.py) для проверки `user_id` по `ALLOWED_TELEGRAM_USERS`, ограничения личными чатами (`ChatType.PRIVATE`) и бесшумным игнорированием (stealth mode) неавторизованных пользователей.
  * Обработчики команд:
    * `/start` — приветствие и список доступных действий.
    * `/help` — подробная справка с разграничением реализованных и запланированных команд.
    * `/status` — состояние бота, окружения, рабочих директорий и доступности CLI с маскированием конфиденциальных данных.
    * `/workspace` — список зарегистрированных рабочих каталогов с проверкой фактического существования на диске (без раскрытия абсолютных путей в интерфейсе).
    * `/run` — интерактивный FSM-мастер выбора дисков и подпапок с пагинацией, либо прямой запуск `/run <alias> <prompt>`, предварительная интерпретация задачи агентом в 1–2 предложениях, автоматическая классификация задачи (`action`, `query`, `complex`) с адаптивным выбором глубины рассуждений (`--effort low|medium|high`), интерактивная кнопка циклического переключения режима (`ef:<id>`), валидация параметров, Inline-кнопки подтверждения («✅ Да, запустить», «❌ Нет, отменить»).
    * Плейсхолдеры для `/wake`, `/tasks`, `/cancel` с информированием о разработке на последующих этапах.
  * In-memory хранилище подтверждений [`ConfirmationStore`](../src/remote_control/controller/confirmation.py) с TTL (по умолчанию 120 с), хранением выбранного уровня рассуждений (`effort`) и защитой от двойных кликов/race conditions через атомарный переход в статус `EXECUTING`.
  * Блокировка параллелизма задач (`asyncio.Lock`) — строго одна активная задача CLI.
  * Модуль классификации задач [`TaskProfile`](../src/remote_control/agent/classifier.py):
    * `action` (простые действия ОС, запуск приложений, создание/удаление файлов) — `--effort low` с требованием лаконичного ответа в 1 предложение без лишних отчётов и листингов PowerShell.
    * `query` (поиск данных, чтение файлов, списки процессов) — `--effort low` с требованием структурированного вывода (таблица/список).
    * `complex` (отладка, исправление ошибок, архитектурный рефакторинг) — `--effort high` с глубоким анализом и проверками.
  * Защита от закрытия процессов Windows при выходе CLI (`Invoke-CimMethod` Win32_Process с рабочей директорией).
  * Форматирование результатов выполнения задачи: экранирование спецсимволов HTML, отображение предупреждений о soft-denied действиях, автоматическая отправка полного файла `task_output.txt` при выводе более 3000 символов, кнопки быстрого перезапуска в той же папке (`💬 Новый запрос`) и смены директории (`📁 Сменить директорию`).
  * Консольная точка входа `remote-control-bot` ([`main.py`](../src/remote_control/controller/main.py)) с корректной диагностикой при отсутствии токена и graceful shutdown.
* **Критерии приёмки**:
  * Сообщения и callback-запросы от авторизованных пользователей успешно обрабатываются.
  * Неавторизованные пользователи бесшумно игнорируются (без ответа в Telegram); аудит-лог фиксирует только `user_id` и timestamp.
  * Запуск задач через `/run` не инициируется до явного нажатия кнопки «Подтвердить запуск».
  * Дочерние GUI-процессы Windows остаются запущенными в системе после завершения сессии CLI.
  * Токен бота читается строго из окружения/.env и никогда не выводится в открытом виде.
  * Набор из 133 модульных тестов с полным мокированием Telegram API и AgyClient проходит успешно без внешних сетевых вызовов.
  * Линтер `ruff` проходит с 0 ошибок.

### Этап 5. Реализация очереди задач и истории в SQLite [Завершён]
* **Цель**: Разработка долговременной очереди заданий, отказоустойчивого SQLite-хранилища истории с автоматическим восстановлением при перезапуске, защита от параллельного запуска нескольких инстансов и реализация команд управления `/tasks`, `/cancel`, `/result`.
* **Результат**:
  * Модуль долговременного хранения задач [`TaskStore`](../src/remote_control/controller/task_store.py) на базе SQLite (`data/tasks.sqlite3`):
    * Автоматическое создание родительского каталога `data/` и безопасная изоляция от Git (`.gitignore`).
    * Режим WAL (`PRAGMA journal_mode=WAL`), таймаут занятости (`PRAGMA busy_timeout=5000`) и внешние ключи.
    * Механизм версионирования схемы через `PRAGMA user_version = 1` с автоматическим накатыванием миграций при старте.
    * Полноценная схема таблицы `tasks` (целочисленный автоинкрементный `id`, уникальный `confirmation_id`, `user_id`, `chat_id`, `workspace_alias`, `working_directory`, `prompt`, `effort`, `status`, `created_at`, `confirmed_at`, `queued_at`, `started_at`, `finished_at`, `duration_seconds`, `exit_code`, `conversation_id`, `result_text`, `result_file_path`, `error_message`, `warning_message`, `raw_stderr`).
    * Даты в формате ISO 8601 (UTC).
    * Безопасное файловое хранилище результатов (`data/results/`) с защитой от Path Traversal, ограничением размера файлов (10 МБ) и автоматическим созданием директории.
    * Восстановление после сбоев и перезапусков (`recover_on_startup`): зависшие задачи со статусом `RUNNING` маркируются как `INTERRUPTED` с диагностической пометкой (без опасного автоматического перезапуска), а задачи в статусе `QUEUED` сохраняются в очереди.
  * Механизм защиты от параллельного запуска нескольких процессов бота [`SingleInstanceLock`](../src/remote_control/controller/single_instance.py):
    * Неблокирующая блокировка на уровне дескриптора файла ОС (`.instance.lock` через `msvcrt.locking` на Windows и `fcntl.flock` на POSIX).
    * Гарантированное автоматическое освобождение блокировки операционной системой при любом завершении процесса (включая нештатный сбой).
    * Информативное логирование и безопасный выход с кодом 1 при попытке запуска второго экземпляра.
  * Фоновый асинхронный исполнитель очереди [`TaskQueue`](../src/remote_control/controller/task_queue.py):
    * Строго последовательное исполнение (concurrency = 1) в порядке FIFO.
    * Реактивное пробуждение через `asyncio.Event` при появлении новых подтверждённых задач, без холостого поллинга CPU.
    * Атомарный перевод задач между статусами (`QUEUED` -> `RUNNING` -> `COMPLETED`/`PARTIAL_SUCCESS`/`FAILED`/`CANCELED`/`INTERRUPTED`).
    * Автоматическая доставка уведомлений о начале исполнения и итоговых результатов в Telegram инициатору задачи (включая прикрепление файлов для длинных ответов).
    * Корректная поддержка отмены выполняемой задачи с распространением прерывания в дерево процессов Windows `AgyClient` и переводом в статус `CANCELED`.
    * Санитизация секретов в логах очереди и Telegram-сообщениях.
  * Полноценные Telegram-обработчики команд управления ([`tasks.py`](../src/remote_control/controller/handlers/tasks.py)):
    * `/tasks` — просмотр последних 10 задач пользователя с наглядными эмодзи-статусами на русском языке, директорией, временем создания и длительностью выполнения.
    * `/cancel <id>` — отмена задачи: мгновенная отмена для заданий в статусе `QUEUED` в БД, безопасная остановка подпроцесса для активной задачи в статусе `RUNNING`, валидация авторства задачи (защита от отмены чужих задач).
    * `/result <id>` — получение сохранённого результата выполнения: текстовый ответ (до 3000 символов) либо выгрузка полного файла `task_<id>_output.txt` в виде документа Telegram, валидация прав доступа (только инициатор задачи).
    * Бесшовная интеграция с подтверждением `/run`: при подтверждении задача ставится в SQLite-очередь, пользователю сообщается позиция в очереди, и фоновый исполнитель мгновенно активируется.
* **Критерии приёмки**:
  * Очередь задач сохраняется между перезапусками процесса бота;
  * Незавершённые задачи `RUNNING` при перезапуске корректно получают статус `INTERRUPTED`;
  * Гарантирован строгий параллелизм (не более одной активной задачи CLI);
  * Повторный запуск бота при уже запущенном процессе штатно отклоняется блокировкой `SingleInstanceLock`;
  * Все команды `/tasks`, `/cancel <id>` и `/result <id>` полностью функциональны и защищены проверкой авторства;
  * 165 автоматических тестов проходят успешно (32 новых теста для хранилища, очереди, команд и блокировки);
  * Линтер `ruff` проходит с 0 ошибок.

### Этап 6. Реализация Wake-on-LAN [Завершён]
* **Цель**: Создание модуля формирования и отправки UDP Magic Packet для удалённого пробуждения целевого Windows-ПК.
* **Результат**:
  * Модуль [`src/remote_control/common/wol.py`](../src/remote_control/common/wol.py) с валидацией MAC-адреса, генерацией стандартизированного 102-байтного Magic Packet (`create_magic_packet`), 3-кратной отправкой UDP-пакета на порт 9 (`send_wake_on_lan`).
  * Функции неблокирующего TCP-опроса доступности (`check_host_availability`, `wait_for_host`) с адаптивной задержкой.
  * Обработчик команды `/wake` в Telegram ([`base.py`](../src/remote_control/controller/handlers/base.py)) с многоэтапной прогрессией: предварительная проверка онлайн-статуса хоста, отправка пакетов, неблокирующее ожидание отклика и понятные статусные сообщения пользователю.
  * 21 модульный тест для WoL-модуля и обработчика.
* **Критерии приёмки**:
  * Magic Packet формируется строго по стандарту (6x 0xFF + 16x MAC = 102 байта).
  * Команда `/wake` не отправляет пакет, если хост уже имеет статус `Online`.
  * Чёткое разделение в логике и интерфейсе: отправка UDP-пакета и реальное включение хоста подтверждаются отдельными статусами.
  * Все тесты проходят успешно (`21 passed`).

### Этап 7. Связь Controller и Windows Agent (при раздельном режиме) [Завершён]
* **Цель**: Реализация защищённого канала связи между постоянным Контроллером (Android Termux) и Windows Agent на целевом ПК.
* **Результат**:
  * Реализован сетевой протокол v2.0 на базе HTTP/1.1 (`/api/v1/*`) с взаимной криптографической аутентификацией `HMAC-SHA256` (`X-Agent-Id`, `X-Timestamp`, `X-Signature`) и защитой от Replay-атак по временной метке.
  * Реализован `AgentDispatcher` на Контроллере: отслеживание heartbeat, учет статуса online/offline, передача скриншотов, управление отменами задач.
  * Реализован `AgentRunner` и `AgentHttpClient` на Windows: фоновый опрос очереди с интервалом 250–500 мс, отправка heartbeat каждые 10 с, последовательное выполнение задач через `AgyClient` (concurrency = 1).
  * Реализована реактивная пауза очереди: задачи ставятся в очередь при выключенном ПК, а при включении ПК и первом heartbeat возобновляются мгновенно через `queue.notify()`.
  * Реализован механизм кооперативной отмены задач: передача списка `cancel_task_ids` в ответах heartbeat и немедленное прерывание процесса через `taskkill /T /F`.
  * Двухрежимная поддержка: `CONTROLLER_MODE=local` (монолитный) и `CONTROLLER_MODE=distributed` (Android Controller + Windows Agent).
* **Критерии приёмки**:
  * Windows Agent автоматически подключается и восстанавливает связь после перезагрузки или потери сети.
  * Задачи из очереди Контроллера поступают Агенту строго после подтверждения пользователем в Telegram.
  * Неавторизованные сетевые подключения к Контроллеру немедленно отклоняются (HTTP 401 Unauthorized).
  * Вызовы Telegram Bot API выполняет исключительно Android Controller; Windows Agent не опрашивает Telegram.
