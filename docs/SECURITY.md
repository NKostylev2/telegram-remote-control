# Модель угроз и политика безопасности (docs/SECURITY.md)

Документ определяет архитектурные принципы безопасности, начальную модель угроз и защитные меры для системы **Telegram Remote Control**.

---

## 1. Фундаментальные принципы безопасности

1. **Принцип минимальных привилегий (Least Privilege)**:
   * Службы Контроллера и Windows Agent должны функционировать под учётными записями с минимальными правами, достаточными для выполнения задач.
   * Windows Agent не должен запускаться от имени суперпользователя `SYSTEM` (`LocalSystem`), если для работы Antigravity CLI достаточно прав стандартного пользователя рабочей станции.
2. **Строгие белые списки (Allowlists) и политика умолчания**:
   * **По умолчанию запрещены все пользователи**: Доступ к боту имеют только Telegram `user_id` из списка `ALLOWED_TELEGRAM_USERS`. Все остальные запросы отбрасываются.
   * **Режим скрытности (Stealth-режим)**: Запросы от неавторизованных пользователей игнорируются **без ответа** в Telegram, чтобы скрыть факт существования сервиса.
   * **Минимальный аудит**: Внутреннее логирование попыток несанкционированного доступа допускается строго с минимально необходимым объёмом данных: числовой `user_id` и временная метка (timestamp).
   * **Рабочие директории**: Задачи могут выполняться исключительно в каталогах из белого списка `ALLOWED_WORKSPACES`, выбираемых через команду `/workspace`.
3. **Запрет произвольного выполнения системных команд**:
   * Через Telegram **категорически запрещено** передавать и выполнять произвольные shell-команды (`cmd.exe`, `powershell.exe`, `bash`).
   * Допускается запуск только бинарного файла Antigravity CLI (`agy`) с фиксированными параметрами пакетного режима. Аргументы передаются в вызов подпроцесса списком (без оболочки `shell=True`), что исключает инъекции команд ОС.
4. **Безопасное хранение секретов**:
   * Токены Telegram Bot API, ключи аутентификации узлов и персональные данные запрещено коммитить в систему контроля версий.
   * Конфигурация считывается из локального файла `.env`, защищённого правами доступа ОС, с предоставлением шаблона `.env.example`.
5. **Обязательное подтверждение чувствительных операций (Human Confirmation)**:
   * **Запуск задачи (`/run`)**: Перед передачей задачи агенту бот обязан показать Inline-кнопки подтверждения («Подтвердить запуск» / «Отмена») с указанием целевой рабочей директории и текста задачи. Без нажатия кнопки подтверждения задача не исполняется.
   * **Прерывание задачи (`/cancel`)**: Остановка активного процесса CLI также требует обязательного подтверждения пользователем.

## 2. Анализ угроз и защитные меры

В таблице ниже детально рассмотрены ключевые векторы угроз, их возможные последствия, механизмы защиты и остаточные риски.

| Угроза | Последствия | Меры защиты | Остаточные риски |
| :--- | :--- | :--- | :--- |
| **1. Несанкционированное использование бота** | Посторонние лица могут обнаружить публичного бота, слать команды, спамить, инициировать запуск ПК или задач. | • Валидация каждого входящего сообщения по `from.id` против списка `ALLOWED_TELEGRAM_USERS`.<br>• Сообщения от неизвестных ID игнорируются без ответа (stealth-режим), чтобы скрыть назначение бота.<br>• Логирование попыток несанкционированного доступа строго с минимальными данными (`user_id`, timestamp). | Компрометация Telegram-аккаунта доверенного пользователя (перехват SMS, троян на телефоне). |
| **2. Утечка Telegram-токена** | Злоумышленник может перехватить бота, перехватывать входящие апдейты, отправлять сообщения от лица бота. | • Хранение токена только в файле `.env`, добавленном в `.gitignore`.<br>• Возможность мгновенной ротации токена через `@BotFather`.<br>• Запрет вывода токена в консоль, журналы или отладочные экраны. | Физический или удалённый взлом машины, где хранится `.env`. |
| **3. Компрометация учётных данных агента** | Поддельный агент или контроллер может перехватить задачи или отправить вредоносные команды в сеть. | • Взаимная аутентификация между Контроллером и Windows Agent (Pre-Shared Key / mTLS / HMAC-подпись сообщений).<br>• Ограничение сетевого взаимодействия пределами локальной подсети (LAN) или закрытого VPN. | Злоумышленник уже находится внутри доверенной домашней LAN с правами анализа трафика (при отсутствии шифрования канала). |
| **4. Вредоносные инструкции / Prompt Injection** | Модели Antigravity передаётся деструктивная инструкция (например, удалить все файлы проекта или скачать вредоносное ПО). | • Исключение shell-интерпретатора при передаче промпта в CLI.<br>• Внутренние правила Antigravity CLI по безопасности.<br>• Логирование текста всех переданных запросов. | Ошибочные действия LLM внутри репозитория в рамках штатных прав Antigravity. |
| **5. Выход за пределы рабочей директории (Path Traversal)** | Попытка выполнить задачу в корне диска (`C:\`), в каталогах `C:\Windows` или в каталоге с ключами SSH пользователя (`~/.ssh`). | • Каноникализация путей (`os.path.realpath` / `Path.resolve()`).<br>• Проверка, что результирующий путь строго начинается с одной из разрешённых базовых директорий.<br>• Запрет использования относительных путей вида `..` и скрытых симлинков. | Символическая ссылка внутри самого разрешённого репозитория, указывающая наружу, если не включена рекурсивная проверка симлинков. |
| **6. Повторное выполнение задания (Replay Attack)** | Повторная отправка одного и того же сетевого пакета или команды приводит к циклическому перезапуску задачи или поломке кода. | • Каждое задание получает уникальный `task_id` (UUID).<br>• Контроллер отслеживает `update_id` Telegram и отбрасывает дубликаты.<br>• Блокировка одновременного запуска двух задач в одном рабочем каталоге. | Случайный повторный клик пользователя на кнопку подтверждения (блокируется инвалидацией inline-кнопки после первого нажатия). |
| **7. Потеря связи между узлами** | Разрыв соединения между Контроллером и Агентом во время выполнения длительной задачи; зависание статуса. | • Механизм регулярных Heartbeat-сообщений (пинг раз в N секунд).<br>• Таймауты ожидания ответа.<br>• Сохранение локального состояния задачи в базе данных на Агенте; при восстановлении связи статус синхронизируется. | Пользователь узнает о завершении задачи только после восстановления физического подключения к сети. |
| **8. Случайное изменение или удаление файлов** | Задача Antigravity завершается некорректно, испортив исходный код или удалив важные файлы. | • Рекомендация выполнять задачи только в git-репозиториях с чистым состоянием (clean working tree).<br>• Возможность автоматического создания резервной git-ветки (`auto-stash` / `auto-branch`) перед выполнением задачи CLI. | Изменение неверсионированных файлов (untracked files), если они не были закоммичены. |
| **9. Утечка секретов в журналах и ответах Telegram** | Antigravity CLI выводит в консоль API-ключи, токены или переменные окружения, которые бот отправляет в чат Telegram. | • Автоматическая маскировка (Redaction) известных шаблонов ключей (токены Telegram, API ключи OpenAI/Google, пароли) регулярными выражениями перед отправкой в чат и записью в лог.<br>• Запрет логирования содержимого `.env`. | Пользовательские уникальные токены нестандартного формата, не попавшие под шаблоны регулярных выражений. |

## 3. Требования к валидации входящих данных

Все входящие команды от пользователя подлежат строгой валидации до передачи в исполнительные модули:
1. **Команда**: Проверяется по строгому списку разрешённых команд:
   `/start`, `/help`, `/status`, `/wake`, `/workspace`, `/run`, `/tasks`, `/cancel`, `/result`.
   Любой нераспознанный ввод отклоняется.
2. **Рабочее пространство**: Управляется командой `/workspace`. Допускается только выбор из предопределённого списка коротких псевдонимов (например, `frontend_repo`, `backend_api`), сконфигурированных в `ALLOWED_WORKSPACES`. Прямой ввод произвольного пути файловой системы из Telegram запрещён.
3. **Текст промпта**: Проверяется на максимальную длину (не более 2000 символов), очищается от недопустимых управляющих байтов и требует явного подтверждения пользователя перед передачей в CLI.
4. **Управление задачами и результатами**:
   * Для команд `/cancel <id>` и `/result <id>` выполняется обязательная проверка авторства: запросить результат или отменить задачу может только пользователь, который её создал (`task.user_id == from_user.id`).
   * Чтение файлов результатов защищено от атак выхода за пределы каталога (Path Traversal): путь проверяется на вхождение в базовую директорию `TASK_RESULTS_DIR` (`data/results/`).
   * Максимальный размер выгружаемого файла ограничен (10 МБ).
